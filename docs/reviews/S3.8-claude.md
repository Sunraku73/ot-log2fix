### Diagnosi

- **8b, thinking on:** in tutte le run root cause corretta (ORA-01653, tablespace `OTCS_SYNTH_DATA` pieno, tabelle DVersData/DTreeCore), 2 evidence valide, 3 fix step coerenti, confidenza medium/high.
- **8b, `effort=none`:** su GPU stessa root cause, ma **6/6 run valide la descrivono come "spazio disco"**. È impreciso: ORA-01653 indica un tablespace che non può estendersi (maxsize/autoextend), non per forza il disco pieno. Confidenza sempre `high`, quindi meno calibrata. Su CPU 1 run su 3 è scartata dallo schema per evidence non valida: nel CLI costerebbe un secondo tentativo, quindi il doppio del tempo.
- **4b:** con `effort=none` degenera (6000–7000 token di JSON non valido). Su CPU nessuna risposta valida in nessuna modalità.

### Verdetto F52

Criterio di adozione: latenza CPU sotto 60 s **e** diagnosi equivalente.
- **Latenza: NON soddisfatto.** 8b `effort=none` a caldo su CPU: 53.9 s e 65.3 s. Il prompt da ~2610 token (system di 4923 caratteri) rende il prefill dominante su CPU: anche con soli ~330 token generati la richiesta resta intorno al minuto. Il ragionamento non è l'unica causa alla radice.
- **Qualità: NON equivalente.** "Spazio disco" sistematico, confidenza sempre alta, 1/3 evidence non valide su CPU, collasso del 4b.

**Non adottato: niente `analyze_v1.2`, niente modifiche per Codex.** F51 (timeout 300 s di default) già copre l'8b su CPU (98–101 s). Il tradeoff resta documentato: su GPU `reasoning_effort=none` porta l'8b da 6–7 s a 3 s con diagnosi leggermente meno precisa. Opzioni per v0.2 in F62.
